\chapter{Реализация и экспериментальное исследование системы}\label{ch:ch3}

Глава посвящена программной реализации системы и~экспериментальному
исследованию её работы на~реальной выборке электронной почты. Материал разбит
по~этапам обработки: для~каждого этапа указаны используемые модули, фрагмент
реализации и~результат. Числовые значения и~рисунки относятся к~одному
прогону системы при~фиксированной конфигурации
(см.~раздел~\ref{sec:ch3/setup}).

\section{Среда реализации и организация кода}\label{sec:ch3/impl}

Проект использует Python версии~3.12. Прикладная логика опирается на
\texttt{sentence-transformers} для~построения векторных представлений моделью
\texttt{bge-m3}~\cite{Chen2024BGEM3}, \texttt{hdbscan} для~плотностной
кластеризации~\cite{McInnes2017HDBSCAN}, \texttt{optuna} для~подбора
гиперпараметров~\cite{Akiba2019Optuna}, \texttt{scikit-learn} для~расчёта
метрик и~вспомогательных алгоритмов~\cite{Pedregosa2011sklearn}, \texttt{torch}
как вычислительный бэкенд \texttt{sentence-transformers} и~модели
\texttt{BAAI/bge-m3}~\cite{Paszke2019PyTorch}, \texttt{psycopg} для~доступа
к~СУБД PostgreSQL и~\texttt{argilla}
для~организации интерфейса ручной разметки~\cite{Vila2023Argilla}.

Исходный код~разделён на~слои по~архитектуре
из~главы~\ref{ch:ch2}; таблица~\ref{tab:ch3/modules} показывает назначение
пакетов. Каждый слой отвечает за~отдельный этап обработки и~обменивается данными
со~смежными слоями через явно заданные интерфейсы. При~замене реализации
разработчик меняет один слой, не~переписывая весь процесс.

Инфраструктурные зависимости (PostgreSQL, сервис разметки Argilla) запускаются
через Docker Compose. Это сохраняет одинаковое окружение у~разных исполнителей.

\section{Данные, экспериментальная установка и протокол оценки}\label{sec:ch3/setup}

Эксперимент опирается на~обезличенную выборку писем реального почтового ящика.
Для~сохранения конфиденциальности далее приведены только агрегированные
характеристики корпуса без~содержания отдельных сообщений. После
синхронизации и~нормализации выборка содержит 7107 писем; этап оценки качества
распределяет сообщения по~категориям \texttt{ok}, \texttt{empty} и~\texttt{too\_short},
а~также по~языку (русский / английский). Таблица~\ref{tab:ch3/corpus} содержит
сводный состав выборки.

Конфигурация эксперимента фиксирует параметры, влияющие на~воспроизводимость.
Модель \texttt{BAAI/bge-m3} (версия~\texttt{BAAI-bge-m3-200}, размерность~1024)
строит векторные представления; этапы с~псевдослучайностью (подбор гиперпараметров,
разбиение на~обучающую и~тестовую части, построение прототипов) запускаются
с~начальным значением генератора~42.

Метрики из~главы~\ref{ch:problem} задают протокол оценки. Для~кластеризации
используются внутренние меры из~раздела~\ref{subsec:ch1/cluster/metrics}: индекс
достоверности плотностной кластеризации (DBCV), силуэтный коэффициент и~индекс
Дэвиса--Боулдина. Для~классификатора применяются метрики
раздела~\ref{subsec:ch1/task/metrics}: доля верных ответов (accuracy),
макроусреднённая и~взвешенная меры \( F_1 \), покрытие и~доля писем, отнесённых
к~служебной категории \texttt{other}.

Эталонное тестовое множество состоит из~меток, проверенных человеком. Сценарий
делит данные на~обучающую и~тестовую части \emph{стратифицированно по~классам}:
из~каждого пользовательского класса в~тест попадает фиксированная доля примеров
(30\,\%). Такой протокол оставляет каждый класс и~в~обучении, где по~его примерам
строятся прототипы, и~в~тесте, где эти примеры в~построении прототипов
не~участвуют. Разбиение целиком по~кластерам могло~бы исключить отдельные мелкие
классы из~теста. Начальное значение генератора~42 делает разбиение
детерминированным; для~каждого класса фиксируется поддержка (support), то~есть
число его тестовых примеров. Служебная категория \texttt{other} в~обучении
и~оценке пользовательских классов не~участвует.

\section{Построение векторных представлений}\label{sec:ch3/embed}

Модель \texttt{bge-m3}~\cite{Chen2024BGEM3} преобразует нормализованные письма,
прошедшие фильтр качества, в~плотные векторные представления. Кодировщик работает
пакетами (batch) фиксированного размера, использует вычислительный ресурс GPU,
накапливает полученные векторы и~объединяет их в~единую матрицу
(листинг~\ref{lst:ch3/embeddings}).

\lstinputlisting[language={Python},linerange={149-167},%
    caption={Пакетное построение эмбеддингов и запись в кеш \texttt{.npz}},%
    label={lst:ch3/embeddings}]{listings/embeddings.py}

Система сохраняет матрицу векторов в~файл формата \texttt{.npz} атомарно: сначала
пишет данные во~временный файл, затем переименовывает его через \texttt{os.replace}.
Это предотвращает повреждение кеша при~аварийном завершении. Для~каждого письма
таблица \texttt{email\_embeddings} хранит ссылку на~файл, номер строки в~матрице,
имя и~версию модели; версионирование позволяет пересчитать представления при~смене
модели, не~затирая прежние. Повторный запуск этапа пропускает письма, для~которых
представление уже построено.

После фильтрации по~языку и~качеству кеш содержит 7105 векторов размерности
1024. Объём кеша составляет около~27{,}8~МБ, суммарное время построения занимает
около 4~минут на~графическом ускорителе NVIDIA RTX~5060~Ti (включая загрузку модели).
Дальнейшая разметка и~оценка выполнены на~1000 наиболее свежих письмах
(пять пакетов по~200 сообщений): этот прогон демонстрирует рабочий цикл системы,
а~разметка оставшейся части корпуса выполняется тем~же штатным процессом
и~выходит за~рамки эксперимента.

\section{Кластеризация и подбор параметров}\label{sec:ch3/cluster}

Система выявляет тематическую структуру корпуса плотностной кластеризацией
HDBSCAN~\cite{Campello2013HDBSCAN,McInnes2017HDBSCAN} по~векторным представлениям
писем. HDBSCAN не~требует заранее заданного числа кластеров и~явно выделяет
шумовые точки. Эти свойства подходят почтовому потоку, где значительная доля
писем не~образует плотных тематических групп.

Optuna~\cite{Akiba2019Optuna} подбирает гиперпараметры
\texttt{min\_cluster\_size} и~\texttt{min\_samples} байесовской оптимизацией
(алгоритм выборки TPE). Целевая функция (листинг~\ref{lst:ch3/tuner})
максимизирует индекс DBCV~\cite{Moulavi2014DBCV}, добавляет слагаемые
за~устойчивость кластеров и~уверенность принадлежности и~штрафует избыточную долю
шума. Конфигурации с~числом кластеров вне~заданного диапазона, долей шума выше
порога или~слишком мелкими кластерами получают штрафное значение.

\lstinputlisting[language={Python},linerange={36-97},%
    caption={Целевая функция подбора параметров HDBSCAN (DBCV с добавками)},%
    label={lst:ch3/tuner}]{listings/tuner.py}

Для~сравнения выбраны две опорные конфигурации: HDBSCAN с~параметрами
по~умолчанию и~партиционный метод KMeans~\cite{MacQueen1967KMeans,Arthur2007KMeansPP}.
Число кластеров KMeans равно числу кластеров, найденному настроенным HDBSCAN.
Силуэтный коэффициент~\cite{Rousseeuw1987Silhouette} и~индекс
Дэвиса--Боулдина~\cite{Davies1979DBI} вычисляются на~не-шумовых точках обоих
алгоритмов. Индекс DBCV рассчитан только для~HDBSCAN, поскольку KMeans
не~выделяет шум; доля покрытия (единица минус доля шума) служит контекстом.
Сравнение проведено на~репрезентативном пакете из~200 писем. Чтобы метрики были
сопоставимы, силуэт и~индекс Дэвиса--Боулдина для~всех трёх конфигураций
пересчитаны в~общем пространстве пониженной размерности (UMAP, 25 измерений).
Таблица~\ref{tab:ch3/cluster-compare} показывает, что настроенный HDBSCAN выделяет
шесть содержательных кластеров при~доле шума~2{,}5\,\%. Конфигурация по~умолчанию
даёт два кластера при~37{,}5\,\% шума, а~KMeans, не~обозначая выбросы, плохо
ложится на~многообразие представлений (низкий силуэт).

Запуск Optuna включал 100 испытаний на~репрезентативном пакете (200 писем)
с~фиксированным начальным значением~42. Рис.~\ref{fig:ch3/optuna} показывает
историю значений целевой функции, а~таблица~\ref{tab:ch3/optuna-best} содержит
лучшие параметры и~оценку их важности. На~целевую функцию почти полностью влияет
\texttt{min\_cluster\_size} (важность близка к~единице); \texttt{min\_samples}
даёт слабый вклад.

\section{Ручная проверка и формирование классов}\label{sec:ch3/annot}

Кластеры не~дают готовые классы: эксперт устанавливает их тематический смысл.
Система отбирает представителей из~каждого кластера и~выгружает их в~сервис
разметки Argilla~\cite{Vila2023Argilla}; эксперт присваивает им~класс
или~предлагает новый. Затем модуль импорта \emph{распространяет} метку
представителей на~остальные письма того~же кластера и~сокращает объём ручной
проверки.

Импорт меток работает в~строгом режиме (листинг~\ref{lst:ch3/propagate}). Если
представители одного кластера получили разные метки, модуль признаёт кластер

\section{Классификатор: построение прототипов и оценка}\label{sec:ch3/clf}

Классификатор использует \emph{прототипную} модель над~векторными представлениями
писем. Для~каждого класса сценарий строит от~одного до~\(M_k\) опорных векторов
(прототипов) по~его обучающим эмбеддингам. Класс с~небольшим числом примеров
получает единственный центроид; более крупный класс делится алгоритмом k-средних
на~подгруппы, чтобы многомодальный класс не~сводился к~одному центроиду
(листинг~\ref{lst:ch3/model}). Число прототипов класса \(y_k\) с~\(n_k\)
обучающими письмами задаётся правилом
\[
    M_k=\max\left(1,\,
    \min\left(\texttt{max\_per\_class},
    \left\lfloor\frac{n_k}{\texttt{min\_support\_per\_prototype}}\right\rfloor\right)\right).
\]
Сценарий \(L_2\)-нормирует прототипы, поэтому их скалярное произведение
с~нормированным вектором письма равно косинусной близости. Оценка класса
\(y_k\) равна максимуму этой близости по~прототипам класса:
\[
    s_k(x)=\max_{1\leqslant m\leqslant M_k}
    \bigl\langle \widehat{\varphi}(x), c_{k,m}\bigr\rangle,
\]
где \(\widehat{\varphi}(x)\) "--- нормированный эмбеддинг письма, а \(c_{k,m}\)
"--- \(m\)-й нормированный прототип класса. В~эксперименте используются
\texttt{max\_per\_class}\,=\,5, \texttt{min\_support\_per\_prototype}\,=\,3
и~модель эмбеддингов \texttt{BAAI/bge-m3}. Прототипная схема не~требует обучения
нейросети и~работает при~скромном объёме размеченных данных.

\section{Применение классификатора и порог уверенности}\label{sec:ch3/infer}

При~применении модели модуль кодирует письмо тем~же эмбеддером и~вычисляет
косинусную близость его~вектора ко~всем прототипам. Оценка класса равна максимуму
по~его прототипам; предсказанием становится класс с~наибольшей оценкой. Решающее
правило использует порог уверенности \( \tau \): если близость к~ближайшему
прототипу ниже~\( \tau \), модуль относит письмо к~служебной категории
\texttt{other}; иначе принимает предсказанный класс (листинг~\ref{lst:ch3/threshold}).
Так модель не~выдаёт содержательный класс для~писем, далёких от~всех известных
тем, и~направляет их в~поток ручной проверки.

\lstinputlisting[language={Python},linerange={29-55},%

Порог~\( \tau \) задаёт компромисс между покрытием (долей писем, для~которых

увеличивает долю \texttt{other}, но~повышает надёжность оставшихся решений.

качества при~покрытии из~раздела~\ref{subsec:ch1/dev/success}. В~эксперименте
используется \(\tau=0{,}55\): в~зоне \(\tau\approx0{,}50\text{--}0{,}60\)

\section{Цикл обновления и контроль дрейфа}\label{sec:ch3/loop}

Цикл обновления позволяет системе адаптироваться к~почтовому потоку. Письма,
отнесённые к~категории \texttt{other}, накапливаются в~отдельном буфере; когда
буфер достигает порогового объёма~\( N \), система повторно кластеризует его
и~выявляет новые устойчивые темы. Представители новых кластеров проходят ручную
проверку, затем сценарий перестраивает прототипы на~расширенном наборе классов.
Новый набор заменяет действующий только при~выполнении критериев активации
и~неухудшении ключевых метрик.

В~настоящем прогоне собрана первая версия классификатора (v1): пять пакетов
разметки дали восемь обучаемых классов, по~которым построены прототипы
(таблица~\ref{tab:ch3/versions}). Полный второй виток цикла
«\texttt{other}~\(\to\)~ручная проверка~\(\to\)~прототипы~\(\to\)~активация»
(версия~v2) в~этом прогоне не~запускался: к~моменту сбора метрик буфер
\texttt{other} содержал 87~писем, что ниже порога запуска нового цикла
кластеризации. Прогон проверил сборку версии и~контроль качества, но~полный цикл
обновления реализован частично (критерий успеха №\,4
из~раздела~\ref{subsec:ch1/dev/success}); исследование долговременного дрейфа
концепций выходит за~рамки настоящей работы.

Проверка дрейфа на~стратифицированной отложенной выборке (holdout) контролирует
готовность к~обновлению. Текущие значения составляют macro-F1\,=\,0{,}742
и~покрытие\,=\,0{,}996 при~порогах срабатывания 0{,}60 и~0{,}50 соответственно,
поэтому флаг \texttt{needs\_retrain} не~взведён. В~этой проверке мера~\(F_1\)
усредняется по~всем встретившимся меткам, включая \texttt{other}; каноническое
значение по~восьми пользовательским классам равно 0{,}835
(раздел~\ref{sec:ch3/clf}).
