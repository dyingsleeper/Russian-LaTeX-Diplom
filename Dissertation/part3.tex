\chapter{Реализация и экспериментальное исследование системы}\label{ch:ch3}

Глава посвящена программной реализации системы и~экспериментальному
исследованию её работы на~реальной выборке электронной почты. Материал разбит
по~этапам обработки: для~каждого этапа указаны используемые модули, принятые
параметры и~полученный результат. Числовые значения и~рисунки относятся
к~одному прогону системы при~фиксированной конфигурации
(см.~раздел~\ref{sec:ch3/setup}).

\section{Среда реализации и организация кода}\label{sec:ch3/impl}

Проект использует язык Python версии~3.12. В~реализации применяются
Python-библиотеки: \texttt{sentence-transformers} для~построения векторных
представлений моделью \texttt{bge-m3}~\cite{Chen2024BGEM3}, \texttt{hdbscan}
для~плотностной кластеризации~\cite{McInnes2017HDBSCAN}, \texttt{umap-learn}
для~уменьшения размерности~\cite{McInnes2018UMAP}, \texttt{scikit-learn}
для~расчёта метрик и~вспомогательных алгоритмов~\cite{Pedregosa2011sklearn},
\texttt{torch} как вычислительная основа модели
\texttt{BAAI/bge-m3}~\cite{Paszke2019PyTorch}, \texttt{psycopg} для~доступа
к~СУБД PostgreSQL и~\texttt{argilla} для~передачи писем в~интерфейс ручной
разметки~\cite{Vila2023Argilla}.

Исходный код разделён на~слои по~архитектуре
из~главы~\ref{ch:ch2}. В~таблице~\ref{tab:ch3/modules} приведено назначение
основных пакетов. Каждый слой отвечает за~отдельный этап обработки и~обменивается
данными со~смежными слоями через явно заданные интерфейсы. При~замене реализации
разработчик меняет один слой, не~переписывая весь процесс.

Docker используется для~запуска программ в~изолированных контейнерах. Контейнер
содержит образ программы, её зависимости и~параметры запуска, поэтому окружение
остаётся одинаковым на~разных машинах. Docker Compose описывает несколько
связанных контейнеров в~одном файле и~запускает их общей командой. В~проекте
через Docker Compose поднимаются PostgreSQL, Adminer, сервер Argilla,
Elasticsearch и~Redis. Файл конфигурации приведён в~листинге
\ref{lst:app/docker-compose}.

Argilla используется только как интерфейс ручной разметки: система выгружает
в~него представителей кластеров, а~пользователь назначает им категории. Сервер
Argilla запускается в~отдельном контейнере. По~официальной схеме развёртывания
для~локального запуска ему нужны дополнительные контейнеры с~Elasticsearch
и~Redis; эти зависимости явно указаны в~файле Docker Compose.

не~участвуют. Начальное значение генератора~42 делает разбиение
детерминированным. Служебная категория \texttt{other} в~обучении
пользовательских классов не~участвует.

\section{Синхронизация и нормализация писем}\label{sec:ch3/norm}

Письмо проходит путь \texttt{IMAP}~\(\to\)~сырое MIME-сообщение~\(\to\)~запись
\texttt{RawEmail}~\(\to\)~нормализованная запись \texttt{NormalizedEmail}.
Модуль Python \texttt{data/preprocessing.py} содержит функцию
\texttt{normalize\_text}. Она заменяет ссылки, адреса электронной почты, даты,
время и~числа устойчивыми токенами \texttt{LINK}, \texttt{EMAIL},
\texttt{DATE}, \texttt{TIME}, \texttt{NUM}, затем приводит пробельные символы
к~единому виду. Полный текст модуля приведён в~листинге
\ref{lst:app/preprocessing}. Замена снижает разреженность словаря и~убирает
вариативность, не~значимую для~тематической классификации.

Модуль Python \texttt{email/normalization.py} содержит функцию
\texttt{normalize\_raw\_email}. Она вызывает \texttt{normalize\_text} вместо
дублирования токенизации, извлекает основной текст из~MIME-структуры, срезает
цитаты, подписи и~служебные окончания письма. Полный текст модуля приведён
в~листинге~\ref{lst:app/normalization}.

Типичный результат нормализации виден по~паре «до~/~после»: исходная строка
\texttt{«Ваш заказ 10481 отправлен 05.06.2026, ссылка https://track.example/...»}
после замены токенами принимает вид
\texttt{«Ваш заказ NUM отправлен DATE, ссылка LINK»}. Такое представление
сохраняет смысл сообщения для~классификации и~снижает влияние случайных
идентификаторов.

\section{Построение векторных представлений}\label{sec:ch3/embed}

Python-библиотека \texttt{sentence-transformers} загружает модель
\texttt{BAAI/bge-m3} и~преобразует нормализованные письма в~плотные векторные
представления. Кодировщик обрабатывает письма пакетами фиксированного размера,
накапливает полученные векторы и~объединяет их в~единую матрицу. Полный текст
модуля Python, отвечающего за~построение представлений, приведён
в~листинге~\ref{lst:app/embeddings}.

Система сохраняет матрицу векторов в~файл формата \texttt{.npz} атомарно:
сначала пишет данные во~временный файл, затем переименовывает его через
\texttt{os.replace}. Это предотвращает повреждение файла при~аварийном
завершении. Для~каждого письма таблица \texttt{email\_embeddings} хранит ссылку
на~файл, номер строки в~матрице, имя и~версию модели эмбеддингов. Повторный
запуск этапа пропускает письма, для~которых представление уже построено.

\section{Кластеризация и подбор параметров}\label{sec:ch3/cluster}

Система выявляет тематическую структуру корпуса плотностной кластеризацией
HDBSCAN~\cite{McInnes2017HDBSCAN} по~векторным представлениям писем. Алгоритм
не~требует заранее заданного числа кластеров и~выделяет шумовые точки. Эти
свойства подходят почтовому потоку, где часть писем не~образует плотных
тематических групп.

Перед запуском HDBSCAN система уменьшает размерность эмбеддингов методом UMAP.
В~реализации используется Python-библиотека \texttt{umap-learn}. Пусть
\( z_i \in \mathbb{R}^{1024} \) "--- эмбеддинг \(i\)-го письма, а
\( d(z_i,z_j) \) "--- расстояние между двумя письмами. Для~каждой точки UMAP
ищет \( k \) ближайших соседей, где в~эксперименте \( k=15 \). Локальная
плотность задаётся величинами \( \rho_i \) и~\( \sigma_i \): \(\rho_i\)
соответствует расстоянию до~ближайшего отличного от~нуля соседа, а
\(\sigma_i\) подбирается так, чтобы сумма весов соседей соответствовала
заданному числу соседей. Вес ребра от~точки \(i\) к~точке \(j\) имеет вид
\[
    p_{j|i} =
    \exp\left(
        -\frac{\max(0, d(z_i,z_j)-\rho_i)}{\sigma_i}
    \right),
\]
где \( p_{j|i} \) показывает степень принадлежности точки \(j\) локальной
окрестности точки \(i\). Направленные веса объединяются в~симметричный граф:
\[
    p_{ij}=p_{j|i}+p_{i|j}-p_{j|i}p_{i|j}.
\]
Здесь \( p_{ij} \) "--- итоговый вес связи между письмами \(i\) и~\(j\).
Далее метод ищет точки \( y_i \in \mathbb{R}^{25} \) в~пространстве меньшей
размерности. Близость в~этом пространстве задаётся функцией
\[
    q_{ij}=\frac{1}{1+a\lVert y_i-y_j\rVert^{2b}},
\]
где \( q_{ij} \) "--- вес связи после уменьшения размерности, а параметры
\( a \) и~\( b \) определяются настройкой минимального расстояния между точками.
UMAP подбирает координаты \( y_i \), минимизируя расхождение между весами
\( p_{ij} \) и~\( q_{ij} \):
\[
    L=\sum_{i<j}
    \left(
        p_{ij}\log\frac{p_{ij}}{q_{ij}}+
        (1-p_{ij})\log\frac{1-p_{ij}}{1-q_{ij}}
    \right).
\]
Функция \( L \) штрафует потерю близких соседей и~искусственное сближение
далёких точек. После такого преобразования HDBSCAN получает матрицу
размерности~25, где локальная структура соседства сохранена лучше, чем
при~простом выборе двух координат для~рисунка.

Качество HDBSCAN зависит от~параметров \texttt{min\_cluster\_size}
и~\texttt{min\_samples}. В~эксперименте применяется случайный подбор параметров
с~закреплением наилучшего результата. Для~каждой случайно выбранной пары
система запускает кластеризацию, вычисляет целевую функцию и~сохраняет пару
с~наибольшим значением. Такой способ выбран потому, что параметров всего два,
а~диапазоны малы: для~пакета из~200 писем
\(\texttt{min\_cluster\_size}\in[5,10]\), а
\(\texttt{min\_samples}\in[1,\min(15,\texttt{min\_cluster\_size})]\), то~есть
фактически не~превышает диапазон~1--10.

Целевая функция использует индекс DBCV~\cite{Moulavi2014DBCV}, устойчивость
кластеров, уверенность принадлежности письма к~кластеру и~штраф за~избыточную
долю шума:
\[
    J =
    \mathrm{DBCV}
    + 0{,}1\,\overline{s}
    + 0{,}2\,\overline{m}
    - 0{,}5\,\max(0, r-0{,}35).
\]
Здесь \( J \) "--- значение целевой функции, \( \overline{s} \) "--- средняя
устойчивость найденных кластеров, \( \overline{m} \) "--- средняя уверенность
принадлежности письма назначенному кластеру, \( r \) "--- доля шумовых точек.
Конфигурации с~числом кластеров вне~диапазона 2--20, долей шума выше~0{,}5
или~медианным размером кластера меньше~5 получают штрафное значение. Полный
текст модуля Python для~подбора параметров приведён
в~листинге~\ref{lst:app/tuner}.

Для~сравнения выбраны две опорные конфигурации: HDBSCAN с~параметрами
без~предварительного подбора и~метод K-Means~\cite{MacQueen1967KMeans}.
Число кластеров K-Means равно числу кластеров, найденному HDBSCAN после подбора
параметров. Силуэтный коэффициент~\cite{Rousseeuw1987Silhouette} и~индекс
Дэвиса--Боулдина~\cite{Davies1979DBI} вычисляются на~не-шумовых точках обоих
алгоритмов. Индекс DBCV рассчитан только для~HDBSCAN, поскольку K-Means
не~выделяет шум; доля покрытия служит дополнительным контекстом.

Сравнение проведено на~пакете из~200 писем. Чтобы метрики были сопоставимы,
силуэт и~индекс Дэвиса--Боулдина для~трёх конфигураций пересчитаны в~общем
пространстве UMAP размерности~25. После подбора параметров HDBSCAN выделяет
шесть содержательных кластеров при~доле шума~2{,}5\,\%. Конфигурация
без~предварительного подбора даёт два кластера при~37{,}5\,\% шума, а K-Means,
не~обозначая выбросы, хуже соответствует форме распределения представлений.

\section{Ручная проверка и формирование классов}\label{sec:ch3/annot}

Кластеры не~дают готовые классы: эксперт устанавливает их тематический смысл.
Система отбирает представителей из~каждого кластера и~выгружает их в~Argilla;
пользователь присваивает представителям класс или~служебную категорию
\texttt{other}. Затем модуль Python \texttt{annotation/import\_labels.py}
переносит согласованную метку представителей на~остальные письма того~же
кластера. Полный текст модуля приведён в~листинге
\ref{lst:app/import-labels}.

Импорт меток работает в~строгом режиме. Если представители одного кластера
получили разные метки, модуль признаёт кластер неоднородным и~относит все его
письма к~служебной категории \texttt{other}. При~согласии представителей модуль
присваивает единую метку всем членам кластера: представителям указывает прямой
источник метки, а~для~остальных писем фиксирует перенос метки по~кластеру.
Строгий режим не~допускает противоречиво размеченные кластеры в~обучающую
выборку.

Разметка сформировала набор тематических классов и~служебную категорию
\texttt{other}; их размеры приведены в~таблице~\ref{tab:ch3/classes}.
Из~1000 кластеризованных писем пользователь вручную проверил 345 представителей.
По~источнику метки 295 писем получили её напрямую от~представителя, для~624
писем модуль перенёс метку по~кластеру, а~81 письмо получило служебную метку:
62 из-за разногласия представителей и~19 как шум HDBSCAN. По~итоговому классу
913 писем распределены по~восьми пользовательским классам, а~87 писем отнесены
к~служебной категории \texttt{other}. Предложенный пользователем класс
\texttt{платежи} не~представлен ни~одним письмом: его представители получили
разные метки, поэтому соответствующий кластер не~используется для~обучения.

\section{Классификатор: построение прототипов и оценка}\label{sec:ch3/clf}

Классификатор использует прототипную модель над~векторными представлениями
писем. Пусть \( D_k=\{x_i:y_i=c_k\} \) "--- множество обучающих писем класса
\( c_k \), а \( \widehat{\varphi}(x_i) \) "--- нормированный эмбеддинг письма
\( x_i \). Если класс содержит одну устойчивую группу, его прототип можно
задать центроидом:
\[
    \mu_k=\frac{1}{|D_k|}\sum_{x_i\in D_k}\widehat{\varphi}(x_i),
    \qquad
    \widehat{\mu}_k=\frac{\mu_k}{\lVert \mu_k\rVert}.
\]
Здесь \( \mu_k \) "--- средний вектор класса, а \( \widehat{\mu}_k \) "---
нормированный прототип. Для~крупных классов система строит несколько прототипов:
обучающие эмбеддинги класса делятся методом K-Means на~\( M_k \) подгрупп,
после чего для~каждой подгруппы вычисляется свой центроид.

Число прототипов класса \( c_k \) с~\( n_k \) обучающими письмами задаётся
правилом
\[
    M_k=\max\left(1,\,
    \min\left(M_{\max},
    \left\lfloor\frac{n_k}{q}\right\rfloor\right)\right),
\]
где \( M_{\max}=5 \) "--- максимальное число прототипов класса, а \( q=3 \)
"--- минимальное число обучающих писем на~один прототип. Оценка класса равна
максимальной косинусной близости письма к~прототипам этого класса:
\[
    s_k(x)=\max_{1\leqslant m\leqslant M_k}
    \bigl\langle \widehat{\varphi}(x), \mu_{k,m}\bigr\rangle,
\]
где \( s_k(x) \) "--- оценка принадлежности письма \(x\) классу \(c_k\),
а \( \mu_{k,m} \) "--- \(m\)-й нормированный прототип класса \(c_k\).
Полный текст модуля Python для~построения прототипов приведён
в~листинге~\ref{lst:app/prototypes}.

В~первой главе рассмотрены наивный байесовский классификатор, линейный метод
опорных векторов и~логистическая регрессия. Эти методы строят параметры модели
по~всей обучающей выборке, поэтому при~добавлении нового пользовательского
класса обычно требуется новое обучение модели. Прототипный классификатор
устроен проще: для~новой метки достаточно вычислить прототипы по~её размеченным
письмам и~добавить их к~существующему набору. Эксперимент показывает, что такая
схема даёт приемлемое качество для~исследуемого почтового архива.

Близость прототипов разных классов помогает найти потенциальные зоны путаницы.
Для~каждой пары классов сценарий вычисляет максимальную косинусную близость
их~прототипов и~помечает пару как конфликтную, если близость превышает
порог~0{,}9. В~таблице~\ref{tab:ch3/conflicts} приведены пары с~наибольшими
значениями. Две конфликтные пары, «авторизация\,--\,безопасность» и

\section{Применение классификатора и порог уверенности}\label{sec:ch3/infer}

При~применении классификатора модуль кодирует письмо той~же моделью эмбеддингов
и~вычисляет косинусную близость его~вектора ко~всем прототипам. Предсказанием
становится класс с~наибольшей оценкой:
\[
    \hat{k}(x)=\arg\max_k s_k(x),
    \qquad
    S(x)=\max_k s_k(x),
\]
где \( \hat{k}(x) \) "--- номер класса с~наибольшей оценкой, а \( S(x) \) "---
уверенность классификации для~письма \(x\). Решающее правило использует порог
уверенности \( \tau \):
\[
    a_{\tau}(x)=
    \begin{cases}
        c_{\hat{k}(x)}, & \text{если } S(x)\geqslant\tau,\\
        \texttt{other}, & \text{если } S(x)<\tau.
    \end{cases}
\]
Здесь \( a_{\tau}(x) \) "--- итоговый ответ классификатора при~пороге
\( \tau \). Если близость к~ближайшему прототипу ниже порога, письмо не~получает
содержательный класс и~попадает в~служебную категорию \texttt{other}. Полный
текст модуля Python с~решающим правилом приведён в~листинге
\ref{lst:app/predict}.

Порог~\( \tau \) задаёт компромисс между покрытием и~надёжностью принятых
решений. Повышение~\( \tau \) увеличивает долю \texttt{other}, но~повышает
долю верных ответов среди писем, для~которых система всё же выдала
пользовательский класс. На~рисунке~\ref{fig:ch3/tau} и~в~таблице
\ref{tab:ch3/tau} приведена зависимость показателей от~порога. В~эксперименте
используется \(\tau=0{,}55\): это значение выполняет критерии качества
из~раздела~\ref{subsec:ch1/dev/success} и~сохраняет покрытие близким к~единице.

\section{Обновление набора классов}\label{sec:ch3/loop}

Служебная категория \texttt{other} нужна для~писем, которые не~похожи
на~известные пользовательские классы или~получили противоречивую разметку
представителей. Такие письма сохраняются отдельно и~могут быть отправлены
на~ручную проверку. Если пользователь назначает им новую согласованную метку,
система строит для~этой метки прототипы и~добавляет их к~набору известных
классов.

Такой порядок соответствует прототипной модели: добавление новой категории
сводится к~вычислению её опорных векторов. Не~нужно заново обучать общий набор
весов, как в~линейном методе опорных векторов или~логистической регрессии.
В~рассматриваемом прогоне служебная категория содержит 87~писем. Они сохранены
как материал для~последующей ручной проверки и~не~входят в~обучение
пользовательских классов.
