## Назначение главы

Глава 2 описывает проектирование модульной локальной системы классификации
электронной почты `diplom-ai` как завершённого решения: архитектура приложения,
поток данных, модель хранения, нормализация писем, построение эмбеддингов для
разметки, кластеризация, ручная проверка, обучение классификатора,
классификация входящей почты и цикл переобучения при дрейфе концепций.

Проект — единое модульное Python-приложение без разбиения на отдельные сервисы.
Командная строка упоминается лишь как один из способов запуска. Категория
`other` — технический механизм (см. три точки появления ниже), а не смысловой
центр главы.

## Целевая (готовая) модель системы — ключевые решения

Эти решения определяют содержание главы и заменяют любые формулировки о
незавершённости.

1. **Очередь покрывает все этапы.** Таблица `pipeline_tasks` и `orchestration`
   диспетчеризуют полную цепочку:
   `normalize_email -> embed_email -> cluster_email -> export_argilla ->
   ручная разметка (pending) -> import_argilla -> train_classifier`,
   а также `classify_email` для входящей почты. Ручная разметка моделируется как
   задача в статусе `pending`: пайплайн приостанавливается до завершения ревью
   человеком, после чего `import_argilla` снимает блокировку и цепочка
   продолжается до `train_classifier`. Всё описывается как реализованное.
2. **Классификация входящей почты.** В режиме `run` система классифицирует
   каждое новое письмо активной версией модели и сохраняет результат
   (предсказанный класс, уверенность, версия модели, причина `other`) в таблице
   предсказаний. Низкоуверенные сообщения (по порогу `τ` из гл. 1) получают
   исход `other`.
3. **Тюнер — в дефолтном пайплайне.** Этап `cluster_email` по умолчанию
   запускает подбор параметров HDBSCAN через Optuna (TPE-сэмплер, максимизация
   DBCV с добавками за устойчивость и уверенность принадлежности и штрафом за
   долю шума, при ограничениях допустимости) перед обучением кластеризатора.
4. **`other` как механизм — три точки.** (а) Шум HDBSCAN: выбросы записываются
   меткой `other` (`outlier_direct`). (б) Разногласие представителей кластера в
   strict-режиме: весь кластер уходит в `other` (`disagreement_other`).
   (в) Порог уверенности `τ` на инференсе: низкоуверенные предсказания —
   исход `other`. Излагается низкоакцентно.
5. **Модель данных — 12 таблиц.** Базовые десять: `raw_emails`,
   `normalized_emails`, `email_embeddings`, `cluster_runs`, `cluster_assignments`,
   `cluster_summaries`, `pipeline_tasks`, `class_labels`, `annotation_batches`,
   `email_labels`; плюс две для серверной стороны готовой системы:
   `email_predictions` (предсказание: письмо, версия модели, класс/`other`,
   уверенность, причина `other`, использованный порог) и `model_versions`
   (версия модели, артефакт, статус active/archived, метрики macro-F1, покрытие,
   per-language F1, активация по quality gates).
6. **bootstrap против run.**
   - `bootstrap` выполняется **только при первом запуске** приложения и
     **принудительно** запускает кластеризацию и начальное формирование классов:
     ingest → normalize → embed → cluster → export → [ручная разметка] →
     import → train → активация первой версии модели.
   - `run` работает **постоянно** после bootstrap: ingest → normalize → embed →
     `classify_email` (предсказание + запись, низкоуверенные → `other`).
     Перекластеризация и формирование новых классов запускаются **только когда
     буфер `other` достигает N элементов** (порог в конфигурации). Тогда
     **кластеризуется только буфер `other`**, далее export → [ручная разметка] →
     import → train → активация новой версии по quality gates. Это цикл учёта
     дрейфа концепций.
7. **Признаки классификатора.** bge-m3 используется **только** для кластеризации
   и разметки (этап начального формирования меток). Классификатор `f_θ` —
   отдельная машина, обучаемая на уже размеченных нормализованных текстах
   (контракт `oid,text,label`) в **собственном** обучаемом представлении
   (словарь токенов + эмбеддинги, mean-pooling, линейная голова). Это
   зафиксировано как окончательная архитектура классификатора.

## 2.1 Требования к системе

Инженерные требования готовой системы: локальная обработка содержимого;
read-only синхронизация с ящиком; единое многоязычное представление для
русско-английских текстов на этапе разметки; воспроизводимость и трассируемость
обработки; модульная архитектура без сервисов; ручная проверка кластеров до
обучения; **непрерывная эксплуатация** с автоматической классификацией входящей
почты и циклом переобучения при дрейфе концепций.

## 2.2 Общая архитектура приложения и оркестрация

`diplom-ai` как единое приложение с пакетами по ответственности: `email`,
`storage`, `queueing`, `orchestration`, `clustering`, `annotation`, `training`,
`inference`. Оркестрация: очередь `pipeline_tasks` с последовательным дренажом,
дедуп задач, повторы с backoff. Полная цепочка этапов (решение 1), парковка на
ручной разметке (`pending`), два режима запуска bootstrap/run (решение 6) с
ключевым отличием по триггеру кластеризации.

## 2.4 Синхронизация и нормализация писем

Путь: `IMAP -> raw MIME -> RawEmail -> NormalizedEmail -> normalized_text`.
Read-only IMAP; дедуп по `content_hash` и IMAP UID; сохранение MIME; извлечение
текста из MIME/HTML; удаление CSS, подписей, цитат, футеров (ru/en); замена
ссылок/адресов/дат/времени/чисел на токены `LINK/EMAIL/DATE/TIME/NUM` (регистр
сохраняется); определение языка (ru/en/unknown); оценка качества
(`ok/empty/too_short`).

**Рисунок 2.3** (поток данных) — при необходимости объединить с рис. 2.2.

## 2.5 Построение эмбеддингов (для разметки и кластеризации)

Локальная загрузка модели через SentenceTransformer; модель `BAAI/bge-m3`
(версия `BAAI-bge-m3-100`); батчевое построение; кеш `.npz` + индекс строк в
`email_embeddings`; версионирование `clustering.embeddings.version`; фильтрация
по языку и качеству (`source_filter`). Явно отметить: эмбеддинги служат этапу
начального формирования классов (кластеризация и разметка), классификатор их не
использует (решение 7).

## 2.6 Кластеризация исторической почты

HDBSCAN (euclidean на нормированных векторах ≡ косинус) как основной алгоритм,
KMeans как альтернатива; подбор параметров HDBSCAN через Optuna по DBCV — **часть
дефолтного этапа** (решение 3); метрики запуска (`cluster_runs.metrics`); выбор
представителей по близости к медоиду; TF-IDF top terms; PNG-визуализация.

**Рисунок 2.4** — кластеризация → представители/выбросы → Argilla → разметка.

## 2.7 Ручная проверка и консолидация классов

Argilla как локальный инструмент ревью. Пользователь проверяет представителей,
а не каждое письмо. Поток:
`ClusterRun -> representatives -> Argilla -> user labels -> email_labels`.
Формирование набора (представители + выбросы); создание новых классов;
распространение метки на кластер (`rep_direct`/`cluster_propagation`);
разногласие → `other` (`disagreement_other`); сохранение в `email_labels` и
истории в `annotation_batches`. Эта стадия — задача `pending` в очереди (решение 1).

## 2.8 Классификация, версионирование и цикл переобучения

Классификатор как отдельная машина (решение 7): обучение на training snapshot
`oid,text,label`, полученном из `email_labels`; собственный словарь и обучаемые
эмбеддинги, mean-pooling, линейная голова; артефакты `model.pt`, `vocab.json`,
`label_mapping.json`, `metrics.json`, `training_config.json`; метрики `accuracy`,
`macro_f1`, `weighted_f1`, покрытие и per-language F1; версии в `model_versions`,
активация по quality gates. Инференс (`classify_email`): загрузка активной
версии, предсказание, порог `τ`, запись в `email_predictions`, низкоуверенные →
`other`. Цикл переобучения: `|other| ≥ N` → кластеризация буфера `other` →
ручная разметка → import → train → активация новой версии (решение 6).
